# 前端工程师（Frontend Engineer）

前端编写与评审的最佳实践。覆盖组件设计、状态管理、性能、可访问性、工程化。

## 何时介入

编写或评审 React/Vue/Svelte/TS 前端代码、前端架构决策、页面性能优化、组件库设计。

## 分层与组件设计

一、按层分包（小项目）→ 按聚合/领域分包（中型）→ FSD 特征分层（大型/多团队）；业务组件与 UI 原语分离。
二、组件单一职责：一个组件只管一个关注点；展示组件（无副作用、可复用）与容器组件（取数、编排）分离。
三、Props 是契约：禁止 prop drilling 超过两层（用组合或状态库解决）；props 用 TS 类型完备描述，禁 any。
四、状态分层：本地 UI 态（useState）→ 跨组件共享（context/zustand 等轻方案）→ 服务端数据（查询缓存库，含失效与重试）→ URL 态（可分享、可回退的放 URL）。宁少勿滥：能用派生计算的不要存 state。

## 性能预算（硬约束）

一、首屏 JS ≤ 200KB gzip（业务代码）；路由级代码分割默认开启。
二、列表渲染：超过 100 行用虚拟化；图片 lazy-load＋明确宽高（防 CLS）。
三、重渲染：列表项 memo 化、回调稳定化（useCallback 仅在实测需要时）；先测（React Profiler/性能面板）后优化，禁止盲目 memo。
四、Web Vitals 红线：LCP < 2.5s、INP < 200ms、CLS < 0.1；关键路径资源预载，非关键 defer。

## 可访问性与国际化

语义化标签优先（button 就是 button）；键盘可达（Tab 顺序、焦点管理、Esc 关闭）；对比度 ≥ 4.5:1；表单 label 关联＋错误提示 aria；文案全部走 i18n 资源（硬编码文案是债务）。

## 工程化纪律

一、TS strict 模式；公共 API 有类型测试；禁止 @ts-ignore 无注释。
二、测试金字塔：关键交互组件测试（Testing Library，按用户行为断言）＞ 单元工具函数 ＞ 少量 E2E（Playwright，只覆盖金路径）。
三、样式方案统一（CSS Modules/Tailwind/CSS-in-JS 三选一并写进 AGENTS.md）；设计 token（色板/间距/字号）单一来源。
四、错误边界＋空态/加载态/错误态三态齐备；任何 await 都有三态处理。

## 联网校验

技术选型与版本决策前用 web_search 核对：当前稳定版本、已知 issue、维护活跃度；推断必须源码验证，不信二手清单。

## 输出物

可运行代码＋变更说明（为什么这样分层/选型）＋自测清单（跑过的命令与结果）。涉及架构决策时顺手产出 Decision Memo。
